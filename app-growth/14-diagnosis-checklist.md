# UAC 衰退诊断模板：CPA 恶化时的标准动作

> 查阅时效：2026-10-01。本模板适用于 App 系列（UAC）CPA 异常升高的系统性排查。

## 概述

CPA 恶化时，**第一步永远是拉 Change history**，而不是先套理论。多数衰退的真因是自己动过的东西（预算、出价、素材、转化配置），先排除人为变量，再谈市场和算法。

## 核心内容

### 第一步：拉 Change history（官方工具）

- 路径：Campaigns 菜单 → Change history；保留 **2 年**记录，可按日期、广告系列、变更类型、用户过滤
- 关键用法：变更时间线**直接叠加在效果数据图上**——把 CPA 拐点和变更点对齐，因果关系一目了然
- 看 **User 列**：谁在什么时间改了什么。系统自动变更会显示为 "Google Ads system" 等，可忽略；重点看人工和 API 变更
- 拉取窗口：CPA 拐点**往前至少 14 天**（UAC 的学习与延迟决定了因果有滞后）

### 第二步：指标拆解公式

CPA 只有一个定义：

```
CPA = 花费 / 转化数
```

UAC 场景下逐层拆开，定位恶化发生在**价格端**还是**效率端**：

```
CPA_事件 = CPI / P(事件|安装)
CPI = CPM / IPM × 1000        （IPM = 每千次展示带来的安装数）
```

- **CPA↑** ⟸ CPI↑（买量变贵）或 P(事件|安装)↓（安装后转化率掉了）
- **CPI↑** ⟸ CPM↑（拍卖变贵）或 IPM↓（素材拿量能力掉了）
- **CPM↑** 再拆：版位结构变化（便宜版位份额掉了）vs 版位内涨价（同版位 CPM 上涨）

用 7 天滑动平均对比拐点前后两周，逐层看哪一环断了。注意 iOS 有 SKAN 2–5 天延迟，**拐点判断至少往后留 5 天**再下结论。

### 第三步：常见病因与验证方法

| 病因 | 症状 | 验证方法 |
|---|---|---|
| **预算剧烈变动** | 预算 1 天内翻倍/腰斩后 CPA 爆炸 | Change history 查预算变更时间；对比变更前后边际 CPA |
| **tCPA/tCPI 调整** | 出价上调后 CPA 跟涨 | 查出价变更记录；学习期至少观察 7 天 |
| **素材被下架/移除** | IPM 下降、YouTube 等版位份额坍塌 | 查资产变更；看版位报告的展示份额变化 |
| **转化跟踪故障** | 转化数断崖、P(事件|安装) 骤降 | MMP/Firebase 事件量对比；检查 postback 与 SDK |
| **版位结构漂移** | CPM 上涨但各版位内 CPM 稳定 | 版位报告：各版位展示占比变化 |
| **季节性/竞争** | 全行业 CPM 普涨、无自身变更 | 横向对比其他系列；查拍卖洞察（UAC 无此报告，靠 CPM 推断） |
| **作弊流量混入** | 安装涨、行为真空、留存断崖 | MMP 作弊报告；应用商店数对账 |
| **SKAN 延迟误读** | iOS 转化"看起来"掉了 | 等 5 天回填后再看；对比 MMP 延迟口径 |

### 第四步：处置纪律

- 一次只动一个变量；出价与预算调整间隔 ≥ 3–5 天
- 预算单次上调 ≤ 30%，下调 ≤ 50%
- 学习期/脆弱期不听 Google 的"提高预算"建议
- 任何处置先写假设、再行动、再复盘——诊断文档化

## 实操 checklist

- [ ] 拉 Change history（拐点往前 14 天），标记所有人工变更
- [ ] 拆解 CPA = CPI / P(事件|安装)，定位价格端还是效率端
- [ ] CPI 拆解到 CPM × IPM；CPM 拆解到版位结构 vs 版位内涨价
- [ ] 检查转化跟踪健康（MMP/Firebase 事件量、postback 状态）
- [ ] 检查素材变更（下架、拒登）与版位份额变化
- [ ] iOS 数据留 5 天回填窗口后再下结论
- [ ] 处置单变量、留间隔、文档化假设
